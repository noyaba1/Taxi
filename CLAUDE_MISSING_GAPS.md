# Remaining Gaps and Recommended Fixes

This document summarizes the remaining technical, methodological, reproducibility, and documentation gaps identified in the Porto taxi route-mining project.

## 1. The required route coverage is not fully achieved

The project does not currently produce 100 qualifying routes for every requested minimum-length threshold.

Observed coverage:

| Minimum route length | Clustering | Transition graph | Suffix array |
|---:|---:|---:|---:|
| 1 km | 100 | 100 | 100 |
| 3 km | 100 | 100 | 100 |
| 5 km | 100 | 100 | 100 |
| 10 km | 22 | 14 | 100 |
| 20 km | 0 | 0 | 20 |
| 40 km | 0 | 0 | 0 |

The absence of 100 routes at 20 km and 40 km may be a genuine property of the dataset, but it should be handled explicitly. The final submission should clearly distinguish between:

- "The algorithm failed to find enough routes," and
- "Fewer than 100 routes satisfy the declared support and continuity constraints."

A recommended improvement is to output a coverage report for every threshold containing:

- number of valid routes found;
- support threshold used;
- equivalent support percentage;
- maximum available route length;
- reason fewer than 100 routes were returned.

## 2. The ranking policy may not match the strict wording of the requirement

The main miners currently prioritize routes using support first and route length second:

```python
orderBy(
    F.col("support").desc(),
    F.col("length_km").desc()
)
```

A strict interpretation of the assignment may require selecting the 100 longest routes among those whose support exceeds the required popularity threshold. Under that interpretation, the ordering should be:

```python
orderBy(
    F.col("length_km").desc(),
    F.col("support").desc()
)
```

The safest solution is to produce both views:

1. Top routes by popularity.
2. Longest routes that satisfy the popularity threshold.

The documentation should state explicitly which ranking policy is considered the primary answer to the assignment.

## 3. Popularity thresholds are configured as absolute support counts

The implementation uses different absolute minimum-support values for different route-length configurations and later converts those values into percentages.

This is mathematically valid, but it creates very different notions of popularity across thresholds. For example, a short route may require thousands of trips, while a 20 km route may require only two trips.

This becomes especially important when a route is described as "popular." A route seen in two trips from one taxi is technically frequent under a support threshold of two, but it is not necessarily a meaningful city-level popular route.

Recommended changes:

- expose `min_support_count` and `min_support_percentage` together in every output;
- define a minimum distinct-taxi threshold;
- clearly separate "frequent under the configured threshold" from "operationally popular";
- consider a shared percentage-based threshold where computationally feasible;
- document why different thresholds are necessary for longer routes.

## 4. Some long-route results are not semantically strong

For the 20 km configuration, the available results have extremely low support and limited taxi diversity. At least one of the longest reported routes appears in two trips generated by only one taxi.

This means the output passes the current frequency rule but may not support the intended business conclusion that the route is broadly popular.

Recommended additions:

- require a minimum number of distinct taxis;
- include `support_trips`, `support_taxis`, and `taxi_diversity_ratio` in the final ranking;
- flag routes dominated by a single taxi;
- provide a confidence or usefulness label such as `citywide`, `limited`, or `single-taxi pattern`.

## 5. The approximate miner still generates all candidate windows

The sketch-based miner reduces the cost of exact aggregation, but it still calls the exhaustive window-generation logic before inserting candidates into sketches.

As a result:

- shuffle and aggregation memory are reduced;
- the number of emitted candidate windows remains quadratic in route length;
- candidate generation can still become the dominant scalability bottleneck.

The current method is therefore a memory and communication optimization, not a full asymptotic replacement for exhaustive candidate generation.

Possible improvements include:

- bounded-length candidate generation;
- prefix-based candidate growth;
- partition-local pruning before emission;
- sampling windows before sketch insertion;
- using the suffix-array output as the candidate source for sketch validation;
- explicitly documenting this complexity limitation.

## 6. Approximate-only output does not include exact route length

When the approximate miner is executed in approximate-only mode, the resulting output can contain an empty or unavailable `length_km` field because route length is currently obtained from the exact table.

This should be fixed without requiring exact global aggregation. The route key already contains the H3 sequence, so exact length can be recomputed directly by:

1. splitting the encoded route into H3 cells;
2. obtaining cell centers;
3. summing the distances between consecutive centers.

Every approximate result should include a valid route length before it is written.

## 7. Clustering support can theoretically count one trip more than once

The clustering method splits a trip into multiple continuous segments when spatial gaps are detected. The shared-run logic then operates on the generated segments rather than explicitly counting unique trip identifiers.

A single trip that produces multiple segments may therefore contribute more than once to the cluster-level shared-run threshold.

The final global support recount reduces the impact on the reported support, but candidate selection inside the cluster can still be affected.

Recommended fix:

- preserve `TRIP_ID` for every segment;
- evaluate shared-run coverage using distinct cluster member IDs;
- ensure one trip contributes at most once to the cluster support calculation.

## 8. Full-scale clustering depends on a sample

The clustering method limits the number of trips used to build clusters because a full self-similarity join over the entire dataset is too expensive.

This is a reasonable engineering compromise, but it means:

- discovered route families depend on the sample;
- rare but important clusters may be missed;
- different samples may produce different candidate routes;
- only the final support recount is full-dataset exact.

Recommended improvements:

- make the sampling strategy deterministic;
- document the sampling seed and sample size;
- compare multiple seeds;
- report candidate stability across samples;
- consider stratified sampling by time, taxi, or origin area;
- clearly label the method as sampled candidate discovery plus full-data validation.

## 9. The cloud verification script does not validate every claim described in the documentation

The cloud evidence documentation claims validation of additional outputs, including detailed cleaning rejection reasons and PageRank activity-zone values. The current verification script mainly checks file existence, total trip counts, suffix-array outputs, route coverage, and basic geometry constraints.

This creates a mismatch between documented verification and automated verification.

The verifier should be extended to check at least:

- all major cleaning rejection counts;
- anomaly counts;
- the expected number of activity zones;
- PageRank value sanity and ordering;
- method-specific route counts;
- support and distinct-taxi constraints;
- absence of invalid spatial jumps;
- non-empty length values in every output;
- reproducibility metadata such as configuration and code version.

## 10. Generated outputs required for reproducibility are not included

The archive contains code and reports, but not all generated data products needed to reproduce the analysis without access to the original cloud bucket.

Missing reproducibility artifacts include some or all of the following:

- route-result CSV or Parquet outputs for each method;
- threshold coverage summaries;
- feature and cleaning summaries;
- anomaly reports;
- activity-zone outputs;
- runtime and memory benchmark outputs;
- cloud job metadata;
- a frozen copy of the configuration used for the final run.

The final package should include a compact `results/` directory containing at least the final top-route tables and summary metrics, even if the full intermediate dataset is too large to include.

## 11. The notebook is not self-contained

The main notebook contains useful saved output, but rerunning it requires replacing a placeholder bucket path and having access to external generated files.

A reviewer cannot reproduce the notebook directly from the archive alone.

Recommended fixes:

- add a single configuration cell for the bucket and output root;
- provide a local fallback that reads bundled summary files;
- validate required paths at startup and show a clear error message;
- include a small representative result bundle for offline execution;
- document the exact execution order and expected environment.

## 12. Cloud execution evidence is incomplete for independent verification

There is evidence of the intended cluster size and cloud workflow, but the archive does not contain enough raw evidence to independently verify every reported runtime and result.

Useful missing evidence includes:

- exported Dataproc job list;
- job IDs and final states;
- Spark event logs or selected Spark UI screenshots;
- executor and worker utilization summaries;
- exact start and end timestamps;
- final GCS output listing with file sizes;
- cloud configuration used during the successful run.

A machine-readable `cloud_run_manifest.json` would substantially improve traceability.

## 13. Documentation is not synchronized with the final project state

Several documents describe the cloud run or readiness state differently. Some files appear to reflect a pre-run state, while later reports describe a completed execution.

There are also inconsistent test-count claims across the documentation.

The project should have one authoritative status document containing:

- final execution state;
- final dataset counts;
- methods that ran on sample, mid-scale, and full-scale data;
- known limitations;
- exact number of collected tests;
- exact final configuration;
- links to all generated outputs.

Older readiness or handoff documents should either be updated or clearly marked as historical.

## 14. Automated tests were not demonstrated in a clean reproducible environment

The repository contains a meaningful test suite, but successful execution depends on a specific Python, Spark, Java, and H3 environment.

A clean reproduction procedure should prove that the test suite passes from a fresh environment rather than relying only on the existence of test files.

Recommended additions:

- pin the supported Python version;
- pin Spark, Java, H3, pandas, PyArrow, and related dependencies;
- provide a lock file or fully pinned requirements file;
- add a one-command test runner;
- save the final test report;
- optionally provide a Dockerfile or reproducible Conda environment.

## 15. Method comparison should distinguish exactness, candidate discovery, and final validation

The methods do not all operate under the same guarantees:

- the suffix-array method is intended to be exact at full scale;
- the exhaustive/maximal method is exact but sample-limited;
- clustering discovers candidates from a sample and validates support globally;
- the transition graph grows routes heuristically and validates resulting sequences;
- the sketch method approximates counts after exhaustive candidate emission.

The comparison should explicitly separate:

1. candidate-generation guarantee;
2. support-count guarantee;
3. sample dependence;
4. completeness guarantee;
5. runtime and memory behavior;
6. route-quality interpretation.

Without this separation, readers may incorrectly assume that all methods return equivalent types of results.

## 16. A formal definition of a "popular route" is still needed

The project uses several signals:

- trip support;
- distinct taxi support;
- route length;
- maximality;
- cluster coverage;
- graph-flow continuity.

However, the final business definition of a popular route is not fully standardized across methods.

A final definition should specify:

- whether support is measured by trips or taxis;
- whether repeated trips by the same taxi are allowed to dominate;
- whether route direction matters;
- whether small spatial deviations are treated as the same route;
- whether maximality is required;
- which metric determines ranking;
- which minimum thresholds apply at each route length.

This definition should be established before comparing the outputs of the different algorithms.
